# v0.12 Proposals — Workforce Control Center, next phase

> **Status:** planning only. Nothing here is committed implementation scope. v0.11.0 is the stable baseline;
> every proposal is evaluated independently and may be cut, reordered, or merged. A release/readiness review
> was completed for v0.11.0 (typecheck clean, lint 0 errors / 853 warnings, 186 tests passing / 1 Ollama-gated
> pending, both webpack bundles compile, `develop` clean).

Each proposal records: **problem / motivation**, **proposed scope**, **dependencies on v0.11**, **priority**,
**risks / architectural impact**, and **acceptance criteria**. The "Recommended direction" section sketches a
starter order but does **not** lock the slice plan.

## 1. Approvals & Tasks (complete the human decision loop)

**Problem / motivation**
- The Approvals tab is a read-only list (resolve UI was explicitly deferred as a "later increment" in v0.11
  Slice 8). `task-assignment` / `run-execution` / `config-change` approvals that are pending under a `manual`
  gate can only be approved/rejected via MCP/CLI tools today.
- The Tasks tab is a read-only list. There is no UI for editing task metadata, priority, agent reassignment,
  or closing tasks (Slice 8 explicitly excluded a Task CRUD redesign).

**Proposed scope**
- Approvals: inline Approve / Reject on pending approval cards (with optional acting-employee picker),
  calling the existing `approvals.resolveApproval` / `approve` / `reject` path so deferred ops
  (start-run, apply-config) run exactly as they do today; live status flip + feedback, consistent with the
  Slice 8 `WORKFORCE_DECIDE_FINDING` command-layer pattern.
- Tasks: create / edit (title, type, priority, description, agent, status) / delete on the Tasks tab,
  backed by the existing task service, preserving `task.agent` ↔ run assignment semantics.

**Dependencies on v0.11**
- `approvals.ts` (`pendingApprovals`, `approvalsByStatus`, `resolveApproval`, `approve`, `reject`),
  `gates.ts` (gate modes + `requestApproval`), `approval:review` / `approval:configure` permissions,
  `observability` counts (already pushed to the panel).
- Slice 8 command-layer patterns: `WORKFORCE_DECIDE_FINDING` success/error payloads, `SET_WORKFORCE_APPROVALS`.
- `getDataService` task CRUD + the existing `SET_WORKFORCE_TASKS` DTO.

**Priority:** high — highest every-day human value; closes the last place v0.11 forces CLI/MCP/YAML use.

**Risks / architectural impact**
- Approving an approval performs a side effect; must reuse `approve()` untouched and assert permission
  explicitly (no new authorization model).
- Task edit must not break `run.taskId`/`run.agentId` invariants (e.g., reassign while queued).

**Acceptance criteria**
- A pending approval can be approved/rejected from the UI (named or system actor), state updates immediately,
  the deferred operation is applied by the existing resolver, and audit/events match CLI behavior.
- Task create/edit/delete round-trips against the existing task store with validation errors inline.
- Typecheck, lint (0 errors), full smoke suite, bundles green.

## 2. Autonomous Classification (findings → work)

**Problem / motivation**
- Findings already carry `suggestedTaskType`, `suggestedWorkflow`, `suggestedPriority` (design doc §4/§5), but
  nothing turns a finding into a task or classifies it into a program/workstream. Human still does that by hand;
  the Morroco-style "discovery → task proposals" loop is not autonomous.

**Proposed scope**
- A classification step in the workflow engine (or a `classify` finding service) that consumes a Finding and
  produces a **task proposal** (title/type/priority/suggested workflow) using the LLM worker — output is
  **data, never authority**.
- Proposals enter a review queue: auto-apply when policy allows, otherwise request agent/human validation via
  the existing gates. Idempotent per finding; bounded by a per-pass cap and dedup against open tasks.

**Dependencies on v0.11**
- `findingsService` record fields, workflow `task`/`tool`/`condition` steps, queue + `ollama` worker,
  `approvals.requestApproval` / gates, permissions (`classification:*` to be added under the existing policy
  engine with `lead`/`human` defaults).

**Priority:** medium-high — the core of "autonomous work", but needs Proposal 3-shaped guardrails first.

**Risks / architectural impact**
- LLM output must never trigger work without an authorized path (same rule as tool steps: capability-gated).
- Unbounded task generation — needs dedup (open tasks with same normalized title) and a firing cap.
- New permission id extends the policy matrix; keep additive, non-breaking.

**Acceptance criteria**
- A finding with suggested fields produces a validated task proposal (pending approval when a gate is manual)
- Duplicate proposals are suppressed; per-pass cap respected; no LLM path bypasses a gate
- Deterministic tests (no Ollama) for dedup + gating, gated Ollama test for the classification itself.

## 3. Validation Policy (risk-based)

**Problem / motivation**
- Design doc §8 defines low/medium/high risk → auto-complete / human review / human approval, but current
  finding validation is uniform: always `pending → agent validate → human decide` via `updateStatus`.
- There is no way to express "validated low-risk findings complete automatically."

**Proposed scope**
- A per-finding-class policy (severity/category/workflow → validation depth: `auto` | `agent-review` |
  `human-approval`) layered over the gates, stored in `.SprintDesk/workforce/` and surfaced read-only (edit UI
  later if needed).
- `auto` = validated finding resolves complete without a human; everything else unchanged. Every auto-complete
  is audited and reversible.

**Dependencies on v0.11**
- `validateFinding` / `updateStatus` / `getFindingReviewCounts`, `Finding` severity/category,
  `gates.getApprovalGates`, the policy override mechanics from `capabilityService`/`DEFAULT_POLICY`.

**Priority:** medium — valuable but changes trust semantics; land after 1 and with explicit opt-in.

**Risks / architectural impact**
- Silent auto-approval is the highest-liability behavior in the product; must require an explicit policy file,
  keep full audit + counters, and never change the `pending → approved` history contract.

**Acceptance criteria**
- Configured risk bands drive auto vs human flow; default (no policy file) stays exactly as v0.11.
- Auto-completed findings appear in activity + counts with a `policy:auto` marker and audit entry; can be
  manually reversed.

## 4. LLM / MCP / Credentials Configuration

**Problem / motivation**
- Global LLM providers (`llm/registry.getLLMProvider`), the MCP server registry (`upsertMcpServer` exists),
  and the credential facade (`secret:`/`env:` refs, `saveSecret`/`listSecretNames`) are all YAML/CLI/MCP-only.
- Per-agent config exists (v0.11 Slice 3); the global tooling surface (design doc UI-9) does not.

**Proposed scope**
- A Control Center "Tools" area: provider list + base URL/model editing + connect test; credential editor
  (name/value, writes only to the gitignored `credentials.secret.json`); MCP server registry CRUD +
  enable/disable + capability/tool list (read view); no change to the capability enforcement chain.

**Dependencies on v0.11**
- `credentials/credentialService`, `mcp/registry` + `safety` (read-only), `llm/registry`, `SecretsData`
  load/save, the Slice 8 webview form + command-layer patterns.

**Priority:** medium — biggest remaining usability gap for the "operate everything from the UI" goal.

**Risks / architectural impact**
- Secrets must never appear in tracked YAML or be returned to the webview in cleartext (write-only in UI).
- Server registry edits are global; keep `sprintdesk_*` built-ins immutable.

**Acceptance criteria**
- Create/edit/delete an MCP server; test a provider connection; save/update a `secret:` credential — all from
  the UI, with no tracked-file leakage; capability gates unchanged and still enforced on every call.

## 5. Workflow Authoring

**Problem / motivation**
- Workflows are authored in `.SprintDesk/settings/workflows.yml` only; the Workflows tab is a read-only list.
  `validateWorkflowDefinition` exists but there is no in-editor validation or builder (design doc UI-6).

**Proposed scope**
- A workflow editor in the Control Center: step list (`task` / `loop` / `tool` / `condition`), per-step inputs,
  inline `validateWorkflow` errors, duplicate-id/step-type/condition-reference checks, and a "run preview"
  describing the task/run effect. Persist via the existing `WorkflowStore` — engine and DSL untouched.

**Dependencies on v0.11**
- `workflow/dsl.ts` (`validateWorkflow`, `validateWorkflowDefinition`, `validateStep`), `WorkflowStore`,
  workflow pickers already used by windows/rules, worker-node `Task`/`Tool`/`Condition` step semantics.

**Priority:** medium.

**Risks / architectural impact**
- The DSL is a controlled surface; editing must never bypass validation. Avoid touching `Engine` step
  execution. Guard against changing workflows referenced by a *running* window.

**Acceptance criteria**
- Create/edit/validate a workflow fully in the UI; invalid steps are rejected with field-level errors; saved
  workflows behave identically to YAML-authored ones (same smoke tests pass); window/rule pickers reflect
  changes live.

## 6. Automation Authoring (schedules + event rules)

**Problem / motivation**
- The Schedules tab is read-only (YAML authoring only). The Event Rules create form is minimal and the matcher
  data model supports a single `eventType` / `source` / `payloadKey` / `payloadValue` condition.

**Proposed scope**
- Schedules: create/edit form (cron with live `parseCron` validation, or interval; autonomy level; task
  template; enable/pause), persisted via the schedule store.
- Event rules: extend the create/edit form (name, source, single or multiple payload conditions), keeping
  backwards compatibility; surface matcher errors inline; live "matches this event" test.

**Dependencies on v0.11**
- `scheduler` (`parseCron`, `evaluateCronSchedule`, `runSchedulerPass`), `SchedulesData`/schedule store,
  `eventRulesService.createEventRule`/`updateEventRule`/`ruleMatches`, `EventRuleMatcher` type.

**Priority:** medium.

**Risks / architectural impact**
- Multiple payload conditions on one rule implies a matcher shape change = a (compatible) data-model change;
  keep `payloadKey`/`payloadValue` valid and additive. Cron UX must never write an unparsed expression.

**Acceptance criteria**
- Schedule create/edit with live cron validation and autonomy control; rule authoring with correct
  match/no-match feedback and idempotent firing; all v0.11 rule/schedule tests still pass unchanged.

## Recommended v0.12 direction (draft, not locked)

Suggested first pass, driven by "complete the human loop first, then deepen automation":

1. **Approvals & Tasks** (Proposal 1) — cheapest, highest daily value, reuses Slice 8 patterns.
2. **LLM/MCP/Credentials config** (Proposal 4) — makes the Morroco scenario fully UI-operated.
3. **Workflow + Automation authoring** (Proposals 5, 6) — power-user authoring completes the control surface.
4. **Autonomous Classification** (Proposal 2) — after guardrails land; enables the UI-10 demo.
5. **Validation Policy** (Proposal 3) — last, because it changes safety semantics and should be opt-in.

This ordering is a starting hypothesis. Each proposal should be opened with its own plan + slice sizing, and
v0.11.0 remains the stable baseline throughout.

## Explicitly deferred (not in v0.12 by default)

- Legacy project-management surface (Tasks/Epics/Backlogs/Sprints) migration or removal (design doc §10)
- Team management UI beyond the existing workflow tree
- Dedicated Events / Audit browsing (Activity tab + event store already cover read-only visibility)
- Workstreams / Programs grouping (Epic-like grouping of classified work — see Proposal 2 once it lands)
- Composing multiple `then`-actions inside a single event rule (single workflow trigger today)
- Per-gate editing UI for gate modes themselves (policy config today is file-level)
- Finding → task auto-creation outside the classification proposal
- Export / backup of workforce data; i18n
- Running the Ollama-gated E2E in CI (stays environment-gated)
