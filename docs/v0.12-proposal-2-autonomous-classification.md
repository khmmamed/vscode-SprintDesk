## 0. Goal

Turn pending **findings into task proposals** autonomously — output is **data, never authority**:

1. **Propose** — a pending finding produces one `TaskProposal` (title/type/priority/optional workflow),
   either deterministically from its `suggestedTaskType`/`suggestedWorkflow`/`suggestedPriority` fields or,
   when a model is available, from an LLM classification of the finding text.
2. **Gate** — the proposal is auto-applied only when the `task-proposal` approval gate is `auto` and the
   actor holds `classification:apply`; otherwise it enters the existing approvals queue (new
   `task-proposal` approval type) and is applied on Approve via the existing `approvals.resolveApproval`
   switch. No LLM path ever creates work without an authorized, gated path.
3. **Bound** — idempotent per finding (one proposal max), deduped against open tasks (normalized title),
   and capped per pass (`maxProposalsPerPass`, default 5).

Everything else in Proposal 2 (risk policy, programs/workstreams grouping) is out of scope.

## 2. Slices

Two independently shippable slices. **Slice A** is the deterministic, fully-testable core (no LLM).
**Slice B** adds the LLM classifier + the Control Center trigger/surface. Naming: Proposal 1 consumed
Slice A (approvals) and Slice B (tasks) → these become **v0.12 Slice C** and **v0.12 Slice D** in the
CHANGELOG so labels stay unique across the release. **Slice E** lands the review side of the loop —
proposals become visible and actionable in the Control Center (no scheduler / queue / worker changes).

**Policy (additive)**

  `lead` += `classification:propose, classification:review, classification:apply`;
  `human` += `classification:review, classification:apply`. (`developer`/`observer` unchanged.)

**`src/services/workforce/classification/classificationService.ts`** (new)
- `validateSuggestion(finding): { ok: true; value: { title: string; type: Task['type']; priority: Task['priority']; workflow?: string } } | { ok: false; reason: string }`
  — normalizes the finding's suggested fields against the real `Task` enums; `title` falls back to `finding.title`.
- `createProposal(input): TaskProposal | undefined` — **idempotent**: an existing proposal for `findingId`
  (any status) or an open task (status not `done|cancelled`) whose title normalizes equal → returns the
  existing / `undefined` (dedup). Emits `task.proposal.created`.
- `applyProposal(proposalId, actorId?): TaskProposal | undefined` — `requireEmployeePermission('classification:apply', actorId)`;
  needs an open task → `createProposal` dedup re-check; `createTask` + `dataService.updateTask({ source: 'classification', workflow })`;
  `linkFindingToTask` + `updateStatus(findingId, 'approved', actorId)`; proposal → `applied`; audit + emit `finding.classified`. Errors → `{ ...proposal, status: 'failed', reason }`.
- `runClassificationPass(options?: { limit?: number; now?: Date }): ClassificationPassResult` — walk
  `pendingFindings()` (newest first) with a suggestion, order by `severity` desc, honor `maxProposalsPerPass`;
  per finding: proposal → gate `auto` ? apply immediately (permission-gated) : `gates.requestApproval({ type: 'task-proposal', pending: { op: 'apply-proposal', proposalId } })`.
  Returns `{ scanned, proposed, duplicates, applied, requestedApproval, failed }`.

**Gate wiring**
- `src/services/workforce/approvals.ts:38-46` — add `case 'apply-proposal': classificationService.applyProposal(pending.proposalId, actorId)`.
- `gates.getApprovalGates/setApprovalGate` already generic over `ApprovalType` — no change needed.

**Findings helper**
- `findingsService.linkFindingToTask(findingId, taskId): Finding | undefined` (additive; sets `taskId`, returns updated finding).

**Tests** — new describe `'v0.12 Proposal 2 — autonomous classification (Slice C)'` (no Ollama):
1. A finding with valid suggested fields produces exactly one proposal; re-running `createProposal` for the
   same finding is a no-op (idempotent).
2. Duplicate suppression: an open task with the same normalized title blocks a new proposal; a `done` task does not.
3. Per-pass cap: N findings → at most `maxProposalsPerPass` proposals, highest severity first.
4. Gate manual → requestApproval (`type: 'task-proposal'`) produced, proposal kept `pending`; resolve
   `approved` through `approvals.approve` applies the proposal and links the finding; `rejected` keeps it unapplied.
5. Gate auto + actor without `classification:apply` → no task created (permission gate holds).
6. Invalid suggestion (bad type/priority) → proposal `failed` with reason, no task, service does not throw.

### Slice D — LLM classification + Control Center trigger/surface

**`src/services/workforce/worker/classifier.ts`** (new)

  mode is `ollama` (or a `classifyWithLlm` flag), counting against the same cap/dedup/gate path. Deterministic tests

### Slice E — Review & apply classified proposals (Control Center surface)

Makes the proposal store a first-class review surface: proposals are visible in their own tab and a reviewer
can apply or reject a `pending` proposal directly. **No new service capability beats an explicit `pending` →
`applied` (Apply) or `pending` → `rejected` (Reject) transition** — everything stays within the taxonomy Slice
C introduced (`TaskProposalStatus` already includes `rejected`); no scheduler / queue / worker / gates code
changes. Rejection is deliberately **not** a finding decision: the finding stays `pending` (findings remain
unclassified, so the proposals tab is the single place that reviews classification output).

**`src/services/workforce/classification/classificationService.ts`** (additive)
- `rejectProposal(proposalId: string, actorId?): TaskProposal | undefined`:
  - `requireEmployeePermission('classification:review', actorId)` — throws on deny (identical contract to
    `applyProposal`'s `classification:apply` gate; `DEFAULT_POLICY` gives `review` to `lead`/`reviewer`/`human`,
    not to a plain `agent`).
  - `pending` only: an `applied`/`duplicate`/`failed`/`rejected` proposal returns unchanged (`undefined` for a
    missing id). Transition writes `status: 'rejected'`, `reason: 'rejected by review'`.
  - Emits `task.proposal.rejected` (proposalId/findingId/actorId) + audits `classification.reject`
    (`targetType: 'proposal'`), mirrors `applyProposal` bookkeeping. Never touches the finding.

**Command layer** (`src/commands/workforce/openWorkforceControlCenter.ts`)
- `WORKFORCE_APPLY_PROPOSAL { proposalId }` and `WORKFORCE_REJECT_PROPOSAL { proposalId }` in the async
  dispatcher (next to `WORKFORCE_RUN_CLASSIFICATION`, same pattern as Slice B task actions): call the service,
  `postResponse(requestId, { applied|rejected: true, proposal })`, push a targeted `PROPOSAL_UPDATED` patch,
  `workforceTreeDataProvider.refresh()`, `pushSnapshot`.
- `counts.proposals` added to the `pushSnapshot` counts payload (additive).

**Webview** (`src/webview/workforce/WorkforceControlCenter.tsx`, mirrored DTO `ProposalDto` from Slice D)
- Add `'proposals'` to `WorkforceSection` + `TABS`; stat chip `Proposals N` next to the Approvals chip.
- `PROPOSAL_UPDATED` handler patches the `proposals` list in place (same as `APPROVAL_UPDATED`).
- Proposals tab: newest-first cards with status chip (`pending` amber / `applied` green / `duplicate` /
  `failed` red / `rejected` grey), type/priority/workflow/confidence, reason on non-pending, **Apply** and
  **Reject** buttons on `pending` only, live `WORKFORCE_RESPONSE` feedback (`proposalAction` /
  `proposalActionError`). No new message names beyond the stringy-typed boundary already used.

**Tests** — new describe `'v0.12 Proposal 2 — autonomous classification (Slice E — proposals review)'`:
1. `rejectProposal` on a `pending` proposal (system actor): status → `rejected`, reason set, no task created,
   finding stays `pending`, audit entry added.
2. Rejecting an `applied` or already-`rejected` proposal returns it unchanged (no-op), missing id → `undefined`.
3. Permission gate: a plain `agent` (role `agent`, no `classification:review`) → `rejectProposal` throws with

4. DTO round-trip: `proposalDtos()` maps seeded proposals incl. status/reason/confidence (covers the webview
   contract).
5. Manual-apply path the tab exposes: `applyProposal` on a `pending` proposal (a `lead` actor) applies the task
   + links the finding; calling again on the now-`applied` proposal creates no second task (dedup at apply).

### Slice F — Scheduled / triggered classification passes

Wires classification into the existing scheduler so a schedule can fire a classification pass on its own,
instead of (or in addition to) materializing a task. **The scheduler must trigger the existing pipeline, never
re-implement classification logic** — `runClassificationPass` already honors `maxProposalsPerPass`, the
`task-proposal` gate (`auto` applies / `manual` routes to approvals), and dedups per finding + by title. Fires
must be overlap-safe: the same `lastOccurrenceKey` bookkeeping task schedules already use.

**`src/data/types.ts`** (additive, non-breaking)
- `ScheduleAction = 'task' | 'classify'`; `ScheduleRecord.action?: ScheduleAction` (default `'task'`).
- `ScheduleRecord.taskTemplate?: ScheduleTaskTemplate` (now optional — a classify schedule needs no template).

**`src/services/workforce/scheduler/scheduler.ts`**
- `runSchedulerPass` becomes `async` (the classification branch awaits `runClassificationPass`).
- In the execute path, when `(schedule.action ?? 'task') === 'classify'`:
  - `await runClassificationPass()` (no actor → system identity; respects cap + gate + dedup internally).
  - `updateScheduleState(stores, schedule, occurrenceKey, now, true)` — same runCount/lastRunAt bookkeeping.
  - fired result gains `classification?: ClassificationPassResult` (additive to `ScheduleFiredResult`).
  - `emitEvent('classification.pass', 'scheduler', { scheduleId, occurrenceKey, ...summary })`.
- Task branch unchanged (`schedule.action` absent/task); dry-run autonomy-1 branch unchanged (records only).
- `buildAndAddTask` returns `undefined` and skips when `taskTemplate` is missing (hardening for optional template).

**Command/webview surface** (additive)
- `ScheduleDto` (extension + webview) gains `action: string` (`s.action ?? 'task'`); Schedules tab renders a
  `task` / `classify` chip. No new message names; manual `WORKFORCE_RUN_CLASSIFICATION` untouched.

**Tests** — new describe `'v0.12 Proposal 2 — autonomous classification (Slice F — scheduled passes)'`:
1. Auto gate + classify schedule → fired result carries `classification` (`proposed/applied` = seeded findings),
   proposals applied, tasks created, `classification.pass` emitted once, schedule `runCount` incremented.
2. Manual gate → `requestedApproval = 1`, proposal stays `pending`, no task created (respects gate).
3. Disabled classify schedule → `skipped: ['disabled']`, no pass, no proposals, no `classification.pass`.
4. Cap: 5 findings + `maxProposalsPerPass: 2` → `scanned 5 / proposed 2 / applied 2`.
5. Overlap/idempotency: same-`now`-rerun within the interval → 0 fired (occurrence-key);
   next occurrence fires but `proposed = 0` (nothing pending) → proposals/tasks stay at 1 each.
6. Existing scheduler tests (scheduler.test.ts + control-center) converted: `runSchedulerPass` now `async`
   (~26 `await` call sites + async `it` callbacks).

### Slice G — Proposal editing before Apply

Lets a reviewer adjust the **proposed task payload** of a `pending` proposal before Apply. Editing must
**not** touch the source finding or the classification evidence (confidence, original values) — it changes only
what a future task would be created from. The proposal stays `pending` throughout; nothing below the service
layer changes, and the existing `classification:apply` / `classification:review` gates are reused unchanged.

**`src/data/types.ts`** (additive, optional-only)
- `TaskProposal` gains `editedAt?: string`, `editedBy?: string`, and `edits?: TaskProposalEdit[]` for auditability.
- `TaskProposalTaskPayload { title; type; priority; workflow? }` and
  `TaskProposalEdit { at; by?; before: Partial<TaskProposalTaskPayload>; after: Partial<TaskProposalTaskPayload> }`
  (in-place evidence of what a reviewer changed; original classified values stay in `before`, `confidence` is
  never editable).

**`src/services/workforce/classification/classificationService.ts`** (additive)
- `editProposal(proposalId, changes: Partial<{ title; type; priority; workflow }>, actorId?): TaskProposal | undefined`:
  - `requireEmployeePermission('classification:review', actorId)` — throws on deny (same permission as Reject;
    the reviewer who may reject may also correct the payload).
  - `pending` only: a missing id → `undefined`; a non-`pending` proposal returns unchanged (no-op, same contract
    as apply/reject).
  - Validates the **merged** result (trimmed non-empty `title`, `type ∈ TASK_TYPES`, `priority ∈ TASK_PRIORITIES`;
    empty `workflow` clears it) and throws a specific error on invalid edits; nothing is persisted on failure.
  - Applies the edit (status untouched → stays `pending`), records `editedAt`/`editedBy` + appended `edits`
    entry (`before`/`after` of the payload fields), emits `task.proposal.edited`, audits `classification.edit`
    with `{ findingId, before, after }`. Never modifies the finding.
- `applyProposal` unchanged — it already reads the latest proposal values, so Apply creates the task from the
  edited payload by construction.

**Command/webview surface** (additive, mirrors the Apply/Reject pattern)
- `WORKFORCE_EDIT_PROPOSAL { proposalId, changes }` in the same dispatcher branch; `postResponse(..., { edited: true, proposal })`
  + `pushProposalPatch`. `ProposalDto` (extension + webview) gains `editedAt?: string` and `editCount?: number`.
- Proposals tab: pending cards get an **Edit** button that swaps the card into a small inline form
  (title / type / priority / workflow) with Save + Cancel; Save posts the edit, `PROPOSAL_UPDATED` patches the
  card in place.

**Tests** — new describe `'v0.12 Proposal 2 — autonomous classification (Slice G — proposal editing)'`:
1. Edit success (a `lead` actor): payload fields merge/update, status stays `pending`, `editedAt`/`edits[0].before`
   preserve the original classified values, finding is untouched (title/id unchanged), `classification.edit` audit
   + `task.proposal.edited` event recorded.
2. Invalid edits throw and persist nothing: bad `type`, bad `priority`, blank `title` (proposal unchanged).
3. Non-`pending` no-op: an `applied`/`rejected` proposal returns unchanged; a missing id → `undefined`.
4. Permission gate: plain `agent` throws (`classification:review`); `lead`/`reviewer`/`human` and system succeed.
5. Apply uses edited values: edit then `applyProposal` creates a task with the edited title/type/priority/workflow,
   and the linked finding still carries its original evidence.

## 4. Risks / guardrails

- **Output is data, never authority:** the only code path that creates a task is `applyProposal`, which always
  runs under `classification:apply` AND (when gate is `manual`) a resolved `task-proposal` approval. The LLM
  classifier never calls task services. Slice E adds one **new** transition (`pending → rejected`) that touches
  no task, no finding, and no approval state.
- **Idempotency + boundedness:** proposal keyed by `findingId` (repeat runs no-op) and deduped against open
  tasks by normalized title; `maxProposalsPerPass` caps each pass; all enforced at the service layer so no
  caller can bypass. Apply/Reject from the tab go through the same service functions as the gate path.
- **Import cycle:** `classificationService` imports `gates` only — `approvals.ts` imports `classificationService`
  inside the resolve switch (`apply-proposal`), never the reverse. Check with the existing lint/bundle build.
- **Additive-only types:** Slice E adds **no** members to `ApprovalType`/`ApprovalPending`/`ApprovalGates`/
  `DEFAULT_POLICY`/`TaskProposal` — `rejected` already exists in `TaskProposalStatus`; only a new service
  function + message names are added.
- **Fallback semantics:** unclassifiable findings become `failed` proposals with a reason (observable), never an
  implicit task or a silent drop — the UI shows the failure reason instead of hiding it.
- **Cron/queue invariants:** classification creates tasks and, when gate is auto, tasks only — it must not touch
  run creation, retry backoff, or worker capacity in this slice. Slice E touches neither scheduler nor queue.
- **Scheduler → classification is one-directional:** `scheduler.ts` imports `runClassificationPass` from
  `classificationService`; nothing in the classification→gates→findings chain imports the scheduler, so making
  `runSchedulerPass` async adds no cycle (verified against the lint/bundle build). Scheduled passes inherit every
  existing guardrail (cap, gate, per-finding dedup, title dedup); the scheduler adds its own occurrence-key dedup
  so overlapping fires cannot double-run the pipeline.
- **Editing is scoped to the proposed payload:** `editProposal` can only change `title`/`type`/`priority`/
  `workflow` on a `pending` proposal under `classification:review`; status (stays `pending`), the source finding,
  classification evidence (`confidence`, original values in `edits[].before`), and approval state are never
  touched. Every edit is audited (`classification.edit`) and emitted (`task.proposal.edited`) with a before/after
  trail, so Apply is always traceable back to the reviewer's final values.

## 5. Out of scope for this slice

- Validation/risk policy auto-complete (Proposal 3)
- Programs / workstreams grouping of classified work (Proposal 2 follow-up)
- Edit UI for the `task-proposal` gate or `maxProposalsPerPass` in Control Center (settings via queue.yml/API only)
- Requeue of a `rejected` proposal (a reject is terminal per finding; a future pass can re-propose findings that
  lost their only proposal via a new lifecycle)
- Scheduler-driven classification pass (explicit trigger + manual review only in this slice)
- Applying the finding's own validation decision from the proposals tab (findings stay `pending` on reject)
