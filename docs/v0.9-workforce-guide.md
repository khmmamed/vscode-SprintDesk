# v0.9 — Workforce & Autonomous Work Guide

The end-to-end **workforce runtime** for SprintDesk v0.9: a deterministic, policy-gated pipeline that maps
**Employee → Skills → Tools → Permissions → Task**, executes work through a **Queue → Worker** boundary, and
supervises it with events, approval gates, retries, a scheduler, and a declarative workflow DSL — all without
an LLM in the scheduling path.

This guide covers the shape today (v0.7–v0.9). It builds on two earlier contracts:

- [`v0.5-workforce-contract.md`](v0.5-workforce-contract.md) — skills, RBAC policy, lifecycle gates,
  deterministic `rankEmployees`.
- [`v0.6-worker-contract.md`](v0.6-worker-contract.md) — queue settings, deterministic scheduler pass,
  single transition path, worker runtime.

> ## ⚠️ Experimental status
>
> The workforce runtime is **headless-first**: everything below is exercised by the smoke suite and exposed
> through MCP tools and CLI entry points (`npm run mcp`, `npm run standup`, `npm run worker`). The VS Code UI
> is **not yet wired to it** — no webview planning surface, run inbox, or review dashboard.
>
> **Known limitations**
> - No end-to-end employee execution flow yet: task discovery → assignment/recommendation → dispatch → run →
>   review is not exposed as one coherent flow (roadmap v0.10+, first priority).
> - The workflow DSL's condition evaluation reads **step status only**; LLM/tool outputs are data, never
>   authorization.
> - `AutonomyLevel` `3` is reserved but currently behaves like `2` (no autonomous-approval escalation yet).
> - LLM providers are wired for invocation; autonomous model-driven *decisions* are gated behind approvals.

## 1. Employees & Workforce

Data under `.SprintDesk/workforce/`:

| Artifact | Store | File |
|---|---|---|
| Employees | `EmployeeStore` | `employees.yml` |
| Teams | `EmployeeTeamStore` | `teams.yml` |
| Skill catalog | `SkillStore` | `skills.yml` |
| RBAC policy | `PolicyStore` | `policy.yml` |
| Pending approvals | `ApprovalStore` | `approvals.yml` |

- An **employee** may be a `human` or an `agent` (`Employee.kind`), with a `role` (`agent`/`developer`/…),
  an RBAC `teamRole` (`lead` | `developer` | `reviewer` | `observer` | `agent` | `human`), certified
  `skills: [{ name, level? }]`, legacy `capabilities` (display alias, matched at level 1), and an optional
  `agentConfig` (the tool to run, e.g., `opencode`) for worker dispatch.
- Skills match **case-insensitively** on `name`/`aliases`; an 8-skill catalog is seeded on first use.
  Default `task.type → required skills` mapping (`bug→debugging`, `feature→typescript, vscode-extension,
  apis`, …) lives in `SkillStore.DEFAULT_TYPE_SKILLS`; `Task.requiredSkills` can override.
- `rankEmployees(task, opts)` picks candidates deterministically:
  `skill coverage → run load → status(idle>busy, offline excluded) → name → id`. Offline employees can never
  be assigned or take work.

## 2. Tasks → Runs → Queue → Worker

The canonical execution model, documented in detail in the v0.6 contract:

```
Task ──(runsCreate / workflow / scheduler)──▶ Run (queued)
        ──▶ QueueService.processQueue (deterministic claim pass)
        ──▶ WorkerRuntime.executeRun ──▶ finishRun
```

- **Runs** live in `.SprintDesk/data/runs.yml`; `status ∈ queued | running | completed | failed | cancelled`,
  with `attempts`, `startedAt`/`finishedAt`, `result`/`error`.
- **Trunk writes only:** every run/employee/task-state change flows through `startRun`, `finishRun`, or
  `cancelRun` — handlers and workers never mutate status directly.
- **Queuing paths:** `sprintdesk_runsCreate` (gate `run:create`, refuses offline agents), the v0.8 scheduler,
  and the v0.9 workflow engine. All three enqueue the same way → **one source of truth** for queued work.
- **Worker runtimes** (`workerMode`): `headless` (spawn, `shell:false`, win32 `ENOENT` fallback), `terminal`
  (VS Code integrated terminal), `noop` (deterministic, for tests/dry runs).
- If a run fails, see the **retry policy** (§6) before the task is marked blocked.

## 3. LLM Providers

> Experimental — invocation-ready, decision-gated.

- **Clients:** `ollama` and `openai` behind a credential facade (`providers/`). Each **employee** chooses a
  model via `Employee.modelProfile`.
- **Contract:** model output is *data*. Nothing in the scheduling path, queue, scheduler, or workflow engine
  treats LLM output as authority — approvals and policy still decide.
- Changing an employee's `modelProfile` (or `agentConfig`/`capabilities`) is a **config-change approval**
  when the gate is `manual` (§5).

## 4. MCP Servers

- **Built-in toolset:** 70 `sprintdesk_*` tools over HTTP (port 3847) and stdio, auto-managed via
  `.SprintDesk/project.mcp.json`.
- **Registry:** external MCP servers in `.SprintDesk/mcp/servers.yml` (`McpServerStore`). Tools:
  `sprintdesk_mcpServersList/Add/Update/Remove`, `sprintdesk_mcpToolsList`, `sprintdesk_mcpCheck`.
- **Capability gate:** external tool calls go exclusively through `sprintdesk_mcpCall`, which checks the
  caller's RBAC permissions (`mcp:list`, `mcp:call`) against the server's declared capabilities. The v0.9
  workflow `tool` step routes through the same gated path — it can never bypass capability checks.
- **Strict tool routing:** workflow `tool` steps always call MCP servers; there is no agent-to-agent call path.

## 5. Reviews & Approval Gates

- **Gates:** `approvalGates` lives in queue settings (`.SprintDesk/settings/queue.yml`); each of the three
  gates is `auto` (default) or `manual`:

  | Gate | ApprovalType | Blocks |
  |---|---|---|
  | `taskAssignment` | `task-assignment` | assigning an employee to a task |
  | `runExecution` | `run-execution` | starting a run (claim → start) |
  | `configChange` | `config-change` | editing `modelProfile` / `agentConfig` / `capabilities` |

- **Flow:** when a gate is `manual`, the requested action records an `Approval` in
  `.SprintDesk/workforce/approvals.yml`
  (`status ∈ pending | approved | rejected`, `ApprovalPending` op = `assign-task` | `start-run` |
  `apply-config`) and emits `approval.requested`; the action proceeds only once resolved.
- **Tools:** `sprintdesk_gatesGet`, `sprintdesk_gatesSet`, `sprintdesk_approvalsList`,
  `sprintdesk_approvalsApprove`, `sprintdesk_approvalsReject`, `sprintdesk_employeeConfigure`.
- **RBAC:** `approval:review` / `approval:configure` are granted to `human`, `lead` (part of `DEFAULT_POLICY`).

## 6. Retry Policy

Configured in queue settings (`.SprintDesk/settings/queue.yml`):

| Setting | Default | Meaning |
|---|---|---|
| `runTimeoutMs` | 600000 (10 min) | per-run execution timeout |
| `maxRunRetries` | 1 | requeues allowed per run |
| `retryBackoffMs` | 30000 | base delay before a retry is eligible |

- Failures are **classified**; on retryable classification the run is **requeued** (`requeueRun`, attempts+1,
  `run.retried` event, `availableAt = now + backoff`).
- The scheduler pass **skips retries whose `availableAt` hasn't elapsed** (`retry-delay`), so retries cannot
  hot-loop.
- Workers mark timed-out runs so the queue can requeue them (stuck-run fix).

## 7. Scheduler & Autonomy

> v0.8 — deterministic, idempotent, **no scheduler-side execution**.

- **Schedules** in `.SprintDesk/settings/schedules.yml` (`ScheduleStore`); each `ScheduleRecord` has
  `kind: 'cron' | 'interval'` (`cron` = 5-field deterministic expression; `interval` = `intervalMs`),
  an `enabled` flag, an `autonomyLevel` (`0–3`, default `1`), and a `taskTemplate`
  (`name/title/type/priority/backlog/epicName`).
- **Autonomy levels** bound what a firing may do:

  | Level | Behavior |
  |---|---|
  | `0` | never fires (`autonomy-level-0`) |
  | `1` (default) | **dry-run** — records the occurrence (`schedule.observed`), never creates work |
  | `2` | **execute** — creates a task from the template, enqueues a run via the queue (`run.queued`), emits `schedule.fired` |
  | `3` | reserved (current behavior == `2`) |

- **Idempotency:** each firing is keyed by `lastOccurrenceKey` (minute-precision); a second evaluation in the
  same key is skipped (`duplicate-occurrence`), capped by `MAX_CRON_LOOKBACK_MS` (24 h).
- Skipped schedules report a reason (`disabled`, `invalid-cron`, `no-match`, `interval-not-elapsed`, …).
- The scheduler builds the same queued runs as `runsCreate` — no separate execution path.

## 8. Events & Findings

- `emitEvent(type, source, payload)` persists to `.SprintDesk/data/events.yml` and every transition is
  mirrored in the audit trail (`.SprintDesk/data/audit.yml`, `sprintdesk_auditList`) and history.
- **Lifecycle events:**

  | Event | Source |
  |---|---|
  | `run.queued` | `workflow`, `scheduler` |
  | `run.started` / `run.finished` / `run.retried` / `run.cancelled` / `queue.skip` | `queue` |
  | `schedule.observed` / `schedule.fired` | `scheduler` |
  | `approval.requested` / `approval.resolved` | `gates`, `workforce` |
  | `employee.status` | `workforce` |
  | `workflow.completed` / `workflow.failed` | `workflow` |

- **Findings/Tools:** `sprintdesk_eventsPublish`, `sprintdesk_eventsList`, `sprintdesk_activitySummary`
  (run/queue/employee digest), plus the audit and history tools.

## 9. Workflow DSL

> v0.9 — declarative, deterministic, bounded. Implemented in `src/services/workforce/workflow/`.

- **Definitions** live in `.SprintDesk/settings/workflows.yml` (`WorkflowStore`); engine is
  `executeWorkflow(name, opts)` built on `validateWorkflow`.
- **Four step types:**

  | Step | What it does |
  |---|---|
  | `task` | creates a Task (`source: 'workflow'`, `workflow: <name>`) + a queued Run `run_wf_<workflowId>_<taskId>_<ts>`, emits `run.queued` |
  | `loop` | bounded iteration (`maxIterations` positive integer), injects `iterateVar` via `{var}` interpolation |
  | `tool` | capability-gated MCP call (`callServerTool`); step must declare `agent`; output recorded as data (`{ content, isError, serverId, toolName }`) |
  | `condition` | branches on step **status only** (`always` / `never` / `step-status`) — never on LLM/tool output |

- **Validation rules** (`WorkflowValidationError`): step ids match `/^[a-z][a-zA-Z0-9_.-]*$/`; loops require
  a valid `maxIterations` and identifier `iterateVar`; tool steps require `agent`; no duplicate ids; unknown
  step types and dangling `step-status` references rejected; workflows are non-empty.
- **Failure semantics:** deterministic and fail-fast, with a static `continueOnError?: boolean` escape hatch
  on steps so a *failed* step can be observed and routed into an `else` branch. Abort checks happen at three
  levels (top-level, loop body, condition branch). Emits `workflow.completed` / `workflow.failed`.
- **Ground truth:** the engine never bypasses `QueueService`, never calls agents directly, and never lets
  tool/LLM output change authorization.
