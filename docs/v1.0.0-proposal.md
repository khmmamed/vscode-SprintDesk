# v1.0.0 — Plan-Native Replatform: Architecture & Slice Plan (canonical)

> **Status: implemented (v1.0.0).** Slices A–Q landed on `develop`; the storage boundary and workflow
> architecture described here are the shipped v1.0.0 behavior. The baseline for this plan was `develop` HEAD
> `a44fca0`. The v0.12 proposal documents remain as historical/superseded references.
>
> **Deferred past 1.0.0 (tracked debt, not shipped):** removal of the residual dead `Epic` interface and the
> legacy Epic/Backlog/Sprint constant strings. There is **no Task→Plan migration utility** (Slice O): v1.0
> starts from the Plan-native storage model and no supported legacy workspace format remains to import.
> Section 10 below is the pre-implementation grounding snapshot.
>
> This is a **breaking major** with a hard architectural invariant:
>
> > **In v1.0, a Plan is the only unit that can enter execution. There is no Task compatibility layer underneath it.**

---

## 0. Goal

Replace the current dual architecture — a legacy project-management surface (Tasks/Epics/Backlogs/Sprints
as Markdown + yml) plus a workforce runtime built around the `Task` type — with a single **Plan-native**
runtime organized as two autonomous control layers:

1. **Orchestrator** ("what work should exist?") — ingests `inputs/*.md` (Basket 1, dropped by humans and
   agents) and writes `plans/PLAN-*.md` (the semantic plan artifacts) with an initial classification.
2. **Organizer** ("what is this, how urgent, how complex, who, when?") — a reconciliation engine that
   re-evaluates existing plans only: re-classifies (challenging the Orchestrator's first guess), prioritizes,
   detects dependencies, selects execution mode and agent, and emits execution decisions as events.

Two strict custody rules follow from the architecture:

- **Artifact vs. state:** `plans/*.md` = semantic content (written only by the Orchestrator).
  `database/*.yml` = runtime state (classification/current, scheduling, organization, execution,
  lineage). The Organizer writes **only** the registry and **never** rewrites plan content; a plan whose
  semantics must change produces a new plan version / new plan (preserving lineage), or a
  `plan.replanning.requested` event that becomes a new input.
- **Decide vs. execute:** the Organizer **never** calls a worker. It writes decisions; the Dispatcher
  translates those decisions into execution events; the Queue → Worker chain consumes them.

Everything else in the v0.12 backlog (validation policy, MCP/LLM/credentials config UI, workflow authoring,
automation authoring) is out of scope: the legacy PM surface and the Task type are removed, and the
surviving workforce runtime is absorbed into the Plan-native model.

## 1. Target architecture

```
HUMAN / AGENT
      │
      ▼
 inputs/*.md            (Basket 1 — drop-zone, no schema)
      │
      ▼
 INPUT REGISTRY         (database/inputs.yml — file refs, ingestedAt, plannedFrom)
      │
      ▼
 ORCHESTRATOR           "What work should exist?"
      │  reads input → decomposes → writes content + seeds registry.original
      ▼
 plans/PLAN-*.md        (semantic artifact)  +  database/plans.yml (registry/state)
      │
      ▼
 ORGANIZER              "What/how/when/by whom?"  — reconciliation engine
      │  re-classify · prioritize · dependencies · agent · mode · timing
      │  writes database/plans.yml ONLY · never the plan .md
      │  fundamentally-wrong plan → plan.replanning.requested → new input
      ▼
 execution decision     plan.execution.requested | delayed | reassigned | cancelled | requeued
      │
      ▼
 DISPATCHER             (thin adapter — decisions → Runs with planId)
      │
      ▼
 QUEUE → WORKER         (existing runtimes, Plan-native)
      │
      ▼
 VALIDATOR              (findings at plan level)
      │          │
    PASS        FAIL
      │          ▼
      ▼      RECOVERY ──► plan.replanning.requested / plan.requeued
 CHECKPOINT             (Basket 3 — database/checkpoints.yml)
      │
      ▼
 HUMAN DEPLOYMENT AUTHORIZATION
```

### 1.1 Organizer drivers (hybrid, locked)

| Driver | Mechanism | Purpose |
|---|---|---|
| Event-driven | `input.created`, `plan.created`, `plan.updated`, `plan.requeued`, `plan.failed`, `agent.idle`, `agent.offline`, `execution.completed`, `dependency.completed` → `organizer.trigger` | Responsiveness — react immediately, do not wait for the next interval |
| Scheduled pass | existing scheduler gains `ScheduleAction 'organize'` (`runOrganizerPass`), plus `runSchedulerPass` itself finally wired into production | Consistency safety net — events can be lost/duplicated/stale; the pass reconciles |
| Manual force-run | Control Center button, `sprintdesk_organizerRun` MCP tool, CLI entry | Debugging, recovery, testing, administrative reconciliation |

The Organizer is a **reconciliation engine**: every pass asks "given current system state, what should
happen to every runnable plan?", not "which new plans were created since last time". It must be
**idempotent and convergent** — a pass that changes nothing emits nothing (reuses the scheduler's
occurrence-key dedup for `organize` passes).

```

│   ├── audit.yml        (relocated from data/)

│   ├── approvals.yml    (relocated from workforce/)
│   ├── policy.yml       (relocated from workforce/)
```

`people/` keeps humans and agents in separate files over one shared identity space, with teams joined in
`teams.yml`. Approval gates are configuration and live in `settings/queue.yml` (`approvalGates`), not in
`database/`. Resolved secrets live in `settings/credentials.secret.json` and are referenced by name only.

Boundaries (locked):

| Directory | Kind of data |
|---|---|
| `inputs/`, `plans/` | Semantic content — Markdown, Orchestrator-written, human-readable |
| `database/` | **Runtime state** — yml, machine-owned, the single state boundary |
| `settings/`, `people/`, `mcp/` | Configuration / metadata — user-editable yml + generated metadata |

The current store directory split (`data/`, `workforce/`, `settings/`, `people/`, `mcp/` — see each
`super('<dir>', '<file>', …)` constructor in `src/data/stores/*.ts`) collapses to the above. Existing
Markdown-backed legacy stores (`tasks.yml`, `backlogs.yml`, `epics.yml`, `sprints.yml` + `.md` mirrors)
are removed, not relocated.

## 3. Domain model (new types in `src/data/types.ts`)

All v1.0 state additions are additive to `types.ts`; the `Task`/`Epic`/`Backlog`/`Sprint` types and the
`TaskWorkStatus`/`ScheduleTaskTemplate`-task coupling are deleted in Slice I.

### 3.1 Plan

```yaml
# database/plans.yml
plans:
  - id: PLAN-000001
    file: plans/PLAN-000001.md
    version: 1
    lineage: { supersedes?: string, supersededBy?: string, planIds?: [string] }

    source: { inputId: IN-000001, checkpointId?: string }

    organization:            # Organizer's own state — distinct from scheduling/execution
      status: pending | analyzing | organized | blocked | escalated
      version: 3             # bumped on every organizational decision
      lastRunAt?: string
      lastDecisionAt?: string
      decisionReason?: string

    classification:
      original:              # Orchestrator's first pass (seed)
        { category, urgency, priority, complexity, risk, executionMode }
      current:               # Organizer may correct
        { …, reason?, classifiedBy: { type: agent|human, id } }

    scheduling:
      status: draft | ready | blocked | running | done | failed | cancelled
      mode:   immediate | scheduled | dependency
      scheduledAt?: string
      dependsOn: [string]    # PLAN ids

    execution:
      status: unassigned | assigned | running | completed | failed
      assignedAgent?: string
      assignmentReason?: { capability: [string], availability: string, workload: number }
      runId?: string

    validation:
      decision: passed | failed | revision
      errors: [string]
      artifacts: [string]

    createdAt / updatedAt
```

Classification is **multi-dimensional and independent** (locked):

| Axis | Values |
|---|---|
| `category` | feature · bug · improvement · refactor · research · documentation · test · maintenance · security · infrastructure · data |
| `urgency` | emergency · urgent · normal · low · scheduled |
| `priority` | critical · high · medium · low |
| `complexity` | low · medium · high |
| `risk` | low · medium · high |
| `executionMode` | immediate · async · sync · scheduled · blocked |

`category` and `urgency` are deliberately independent — a bug may be `normal`, and a feature may be
`emergency`. Nothing implies "bug ⇒ urgent".

**Artifact/state invariant:** `plans/PLAN-*.md` holds `# PLAN-…` + `## Objective` + `## Implementation`
+ `## Acceptance Criteria` + `## Constraints`. `database/plans.yml` holds only the metadata above and a
`file` reference. `classification` and `organization` in the registry are **mutable by the Organizer**;
the plan `.md` body is **never** regenerated from registry state (unlike the legacy `saveTaskMd` mirror).

### 3.2 Input, Cycle, Checkpoint

```yaml
# database/inputs.yml
inputs:
  - id: IN-000001
    file: inputs/IN-000001.md
    status: new | planned | failed            # failed → recovery may rewrite/extend
    ingestedAt: …
    plannedFrom: [PLAN-000001, PLAN-000002]   # plans created from this input
    source: { type: human|agent, id?, checkpointId? }

# database/cycles.yml  — one CY-#### per continuous lifecycle round
cycles:
  - id: CY-000001
    inputIds: [IN-000001]
    planIds: [PLAN-000001]
    executionIds: [RUN-…]
    checkpointId?: …
    organizationPasses: 3
    startedAt / closedAt?
    outcome: open | closed-pass | closed-fail | cancelled   # closed at checkpoint (or recovery escalation)

# database/checkpoints.yml  — Basket 3
checkpoints:
  - id: CHK-000001
    planId: PLAN-000001
    runId?: …
    artifacts: [string]                        # validator output refs
    status: ready | deployment-authorizing | deployed | rejected
    deploymentDecision?: { by, at, reason }
```

`Run` (see Slice D) carries `planId` and stays in `database/executions.yml`.

## 4. Component boundaries (locked)

| Component | Responsibility | Writes | Never does |
|---|---|---|---|
| Input layer | Accept anything from humans/agents | `inputs/*.md`, `database/inputs.yml` | — |
| **Orchestrator** | Understand input → decompose → create plans | `plans/*.md` + `registry.original` | re-write an existing plan's content |
| **Organizer** | Re-evaluate, classify, prioritize, schedule, assign | `database/plans.yml` (`organization`/`classification.current`/`scheduling`/`execution`) + events | write plan content; call workers |
| **Dispatcher** | Turn organizer decisions into execution | queued `Run` (planId) via queueService | decide (redundantly with Organizer) |
| **Worker agents** | Execute | run outputs / findings | — |
| **Validator** | Verify | findings/validation state | — |
| **Recovery** | Diagnose / replan failures | new input or `plan.requeued` | — |
| **Checkpoint** | Create Basket 3 artifacts | `database/checkpoints.yml` | — |
| **Human** | Authorize deployment | deployment decision | — |

Every Organizer decision is emitted as an event (`plan.execution.requested | delayed | reassigned |
cancelled | requeued | plan.replanning.requested`) so the audit trail is deterministic and the Dispatcher
(or any future consumer) is decoupled from the classification engine.

## 6. Slices (execute in order; each independently shippable, docs-first)

The A–I structure is locked. Build order follows the dependency chain: content first (A–C), then the
execution seam (D–F), then the loop tail + surface (G–H), then deletion (I).

### Slice A — Plan domain, stores & storage layout

**Types (`src/data/types.ts`, additive):** `Plan`, `PlanOrganizationStatus` (`pending|analyzing|organized|blocked|escalated`),
`PlanClassificationAxis` (the six-axis taxonomy above), `PlanScheduling`, `PlanExecution`, `PlanValidation`,
`PlanLineage`, `PlansData`; `InputRecord`, `InputsData`; `Cycle`, `CyclesData`; `Checkpoint`, `CheckpointsData`.
`Run.planId: string` added **alongside** `taskId` in this slice (deprecated), `taskId` removed in Slice D.

**Stores (`src/data/stores/`, new base dir `database/`):** `PlanStore` (`super('database','plans.yml','plans',…)`),
`InputStore`, `CycleStore`, `CheckpointStore`. Relocate `EventStore` (`data/events.yml` → `database/`),
`AuditStore` (`data/audit.yml` → `database/`), `RunStore` (`data/runs.yml` → `database/executions.yml`,
keep internal key `runs`). Update `stores/index.ts` interfaces + constructor and the activation seeding in
`extension.ts:364-391`.

**Plan markdown round-trip:** `planService.ts` with `writePlanMd(plan)` / `readPlanMd(file)` using
`gray-matter` (already a dependency): front-matter carries `id`/`version`/`lineage`; body holds
Objective/Implementation/Acceptance Criteria/Constraints. **No `savePlanMd` mirror of registry state** —
the `.md` is only ever written by the Orchestrator content path.

**Tests** — `test/smoke/planStore.test.ts`: type/store round-trips; md write/read preserves body; relocated
store paths read legacy data back (seeded `.SprintDesk/data/runs.yml` → `database/executions.yml`).

### Slice B — Orchestrator (Basket 1 → plans)

**`src/services/workforce/orchestrator.ts`** (new):
- `listInputs()` → discover `inputs/*.md` not yet in `InputStore` (file-mtime + content-hash dedup).
- `ingestInput(file)` → `InputRecord` + open `Cycle` (`database/cycles.yml`).
- `orchestrate(inputId, opts)` → deterministic (from front-matter/registry defaults) or LLM (reuse
  `worker/classifier.ts` calling convention) decomposition; for each unit: `createPlan` writes
  `plans/PLAN-*.md` (converted sequentially with a repository numeric counter, `PLAN-####`) + seeds
  `registry.classification.original`. Bounded by `maxPlansPerPass` (queue settings, default 5) and deduped
  against existing plans by normalized objective.
- Emits `plan.created`, `input.planned`, `cycle.opened`. Never writes `classification.current`.

**Guardrails inherited from Proposal-2:** output is data, never authority; idempotent per input; per-pass
cap; title/objective dedup. LLM is confined to decomposition suggestions — no LLM path creates a plan
without the orchestrator content path + cap.

**Tests** — describe `'v1.0.0 Slice B — Orchestrator'`: input discover + ingest; dedup; deterministic
decomposition from front-matter; cap; LLM path with `providerOverride` (gated); `plans/*.md` written with
correct front-matter.

### Slice C — Organizer core (reconciliation)

**`src/services/workforce/plan/organizer.ts`** (new) + **`runOrganizerPass(opts)`**:
- For each plan not `done|cancelled`: reconcile classification (`original → current` when evidence differs,
  sets `classifiedBy` + `reason`), detect dependencies (`dependsOn`), resolve runnability, select
  `executionMode`, and — when a `plan` requires assignment — select an agent via `rankEmployees` against
  plan dimensions.
- Writes only `database/plans.yml` (`organization.status/version/lastRunAt/lastDecisionAt/decisionReason`,
  `classification.current`, `scheduling.*`, `execution.*`).
- **Never writes plan content.** A plan that is fundamentally wrong (e.g., impossible objective, wrong
  domain, no longer relevant) → emits `plan.replanning.requested` with a reason (lineage recorded in the
  registry), and the recovery path (Slice G) turns it into a new input. It is **not** silently rewritten.
- Emission discipline: emits `organizer.pass.completed`; emits `plan.execution.*` **only** on decision
  change (convergent — a no-change pass emits nothing).
- Trigger API: `triggerOrganizer(opts)` for the event path and manual force-run.

**Tests** — describe `'v1.0.0 Slice C — Organizer core'`: re-classification with audit reason; dependency
blocking; mode selection; agent selection against seeded people/skills; no-change pass emits no events;
`organization.version` bumps, `classification.current` distinct from `original`; plan content file hash
unchanged after a pass; fundamentally-wrong plan → `plan.replanning.requested`, no content write.

### Slice D — Plan execution identity (critical seam)

**`src/data/types.ts`:** `Run.taskId` removed; `Run.planId: string` required. `Run` key stays `runs` in
`database/executions.yml`.

**`src/services/workforce/queueService.ts`:** `createRun(planId, agentId)` derives agent/workload/status
from the plan registry, not a task; claim/finish/requeue/cancel write `plan.execution.*` and the plan's
`runId`; `processQueue` skip reasons `plan-not-found` / `plan-not-runnable` (replacing `task-not-found` /
`task-closed`).

**Workers (`worker/worker.ts` + runtimes):** `WorkerRequest` drives `plan.title`/`plan.path`
(plans/**/*.md); timeout/retry/classification semantics untouched. **Findings** (`findingsService.ts`)
link to `planId`.

**Atomic test fixture rewrite** (mandatory in the same commit): `test/helpers/workspace.ts` seeds plans;
the task-based suites convert — `queue.test.ts`, `events.test.ts`, `stores.test.ts`, `workerWorkflow.test.ts`,
`workflow.test.ts`, `scheduler.test.ts`, `workforceControlCenter.test.ts` — all assertions moving

slice (they are removed in Slice H/I) — keep the old task tool handlers alive here so the registry test
passes until the removal slice.

### Slice E — Dispatcher + execution events

**`src/services/workforce/plan/dispatcher.ts`** (new, thin):
- Input: registry state (`organization.status = organized` ∧ `scheduling.status = ready` ∧
  `execution.mode` eligible) or organizer events.
- Action: enqueue via `queueService.createRun(planId, agentId)`. Emits `plan.execution.requested`.
- Handles `delayed` (gates: `scheduling.mode = scheduled` + `scheduledAt`), `reassigned` (agent change),
  `cancelled` (queue remove), `requeued` (recovery).

**Event types added:** `plan.execution.requested | delayed | reassigned | cancelled | requeued`,
`plan.replanning.requested`, `organizer.trigger`, `organizer.pass.completed`, `plan.created`,
`input.planned`, `cycle.opened`. Wired into `eventRulesService` matcher surface (additive).

**Tests** — describe `'v1.0.0 Slice E — Dispatcher'`: organized+ready plan → `Run` with `planId` +
`plan.execution.requested` once; delayed plan not enqueued; reassigned updates agent; cancelled removes;
event-rules can trigger a workflow from `organizer.trigger` without re-entrancy.

### Slice F — Organizer engine wiring (scheduler → production)

**Scheduler (`scheduler/scheduler.ts`):**
- `ScheduleAction` gains `'organize'` (`types.ts:563`); `runSchedulerPass` becomes the reconcile driver:
  `action: 'organize'` → `runOrganizerPass()`; `action: 'task'` → replaced by `'plan'` schedule
  materializing a typed plan template (templates now Plan-shaped).
- **Wire `runSchedulerPass` into production** — the extension activates an interval driver honoring
  `queueSettings.enabled` / `pollIntervalMs` (currently orphaned: `enabled: false`, `pollIntervalMs: 30000`

  (`npm run scheduler`, mirroring `cli/worker.ts`) for headless operation.
- Event path: agent idle/offline + `execution.completed`/`dependency.completed` raise `organizer.trigger`
  (via the existing `subscribeEvents` mechanism).

**Manual force-run:** Control Center button, `sprintdesk_organizerRun` MCP tool, CLI flag.

**Tests** — convert the existing scheduler describe blocks (occurrence-key, autonomy, capability) to
`runSchedulerPass` callers with `action: 'plan'|'organize'`; new: interval driver honors `pollIntervalMs`
and `enabled`; `organize` schedule fires a pass, respects cap, no-change pass fires nothing; agent.idle event
triggers a pass without a schedule.

### Slice G — Recovery, Checkpoint & Deploy authorization

**Recovery (`plan/recovery.ts`):** on `plan.failed` or validator `failed`/`revision` →
classification `escalated` → either `plan.requeued` (retry-eligible, backoff per existing retry policy)
or `plan.replanning.requested` → new `inputs/*.md`/`InputRecord` (Organizer never writes content).
`cycle.outcome` set on escalation.

**Checkpoint (`plan/checkpointService.ts`):** validator pass closes `database/checkpoints.yml`
(`CHK-####`, planId, artifacts, status `ready`), closes the `Cycle` (`closed-pass`), emits `checkpoint.created`,
`cycle.closed`.

**Deploy authorization (gates):** new `deploy` gate (`manual`); `sprintdesk_checkpointsApproveDeploy` /
`RejectDeploy` + Control Center action under new `plan:deploy` permission (`DEFAULT_POLICY` additive).
Approval flows through the existing `approvals.resolveApproval` switch (`op: 'authorize-deploy'`).
Emits `deploy.authorized | deploy.rejected`, `checkpoint.deployed`.

**Tests** — describe `'v1.0.0 Slice G — Recovery/Checkpoint/Deploy'`: fail→requeue with backoff; fail→replan
creates a new input; validator pass closes cycle + writes checkpoint; manual deploy gate requires approval;
reject keeps checkpoint `ready`.

## 8. Risks / guardrails

- **Slice D is the blast radius.** The queue/worker/workflow/findings/execution-window surface and ~7 test
  files key off `taskId`. It must land atomically with its fixture rewrite; no half-migrated `Run`
  (either `taskId` or `planId`, never both). This is the only slice where the legacy layer and the new
  layer must still coexist long enough to pass the registry test.
- **Output is data, never authority** (unchanged rule). The only work-creating path is
  Dispatcher → Queue → Worker under `plan:assign` + gates. The Orchestrator's decomposition and the
  Organizer's classification are LLM-loosened but always pre-gate.
- **Organizer convergence.** Reconciliation must be idempotent: a pass that changes nothing emits no
  events; `organization.version` and `scheduling` only move on actual decision changes. Occurrence-key
  dedup from the scheduler reused for `organize` passes.
- **Custody rules are the product.** Two invariants are enforced by tests, not convention:
  (1) Organizer never writes `plans/*.md` — a pass leaves the plan file content-hash identical;
  (2) Dispatcher, not Organizer, touches the queue — no `queueService` import inside the organizer module.
- **Import cycles.** Organizer imports scheduler/events/gates but never queue/worker; `dispatcher.ts`
  imports queueService only. Check with lint + bundle build.
- **Store path migration is mechanical but broad.** Every `super('<dir>', …)` constructor, the
  `stores/index.ts` wiring, activation seeding, and tests reference paths; the relocation lands store-by-
  store (Slice A moves events/audit/runs; later slices move the rest) rather than one giant churn.
- **Registry-test synchronization.** Old task/epic/sprint/backlog MCP tools must be removed in the same
  slice that updates `registry.test.ts` + manifest/README bootstrap — otherwise the hygiene test fails.
- **The scheduler becomes a production driver.** Once wired, autonomy levels (0=never, 1=dry-run,
  2/3=execute) and `queueSettings.enabled`/`pollIntervalMs` gate real side effects for the first time;
  defaults ship `enabled: false` so nothing runs until a user opts in.
